# TrucksIL: статус и план продолжения

_Дата анализа: 2026-11-14_

## 1. Текущий статус

| Область | Что есть | Оценка |
|---|---|---|
| Код | `index.html` содержит строку `test`, в `src/` только readme и пример профиля грузовика | ~0% |
| Требования | `docs/PRODUCT_REQUIREMENTS.md` (черновик v0.1): профили, маршрутизация, отчёты, таймер смены, 4 языка, приватность | Есть основа |
| Архитектура | `docs/ARCHITECTURE.md`: 6 фаз в общих чертах, стек не выбран | Набросок |
| Данные | `data/restrictions.schema.json`: черновая JSON-схема ограничения | Есть основа |
| Политика данных | `docs/DATA_VERIFICATION.md`: статусы и правила верификации | Хорошая основа |
| Инфраструктура | Нет: ни сборки, ни тестов, ни CI, ни лицензии, ни `.gitignore` | 0% |
| Источники данных | Ни одного подтверждённого официального источника | Блокер |

Проблемы, которые стоит исправить сразу:
- В `README.md` написано `TruckIL`, а проект называется `TrucksIL`. Описания проекта и инструкций запуска нет.
- Есть файлы `readme.md` в нижнем регистре и `README.md` в верхнем. Лучше привести к одному виду.
- В схеме ограничений нет полей `verifier`, `geometry` и лицензии источника, хотя `DATA_VERIFICATION.md` их требует. `unit: "boolean"` применяется к числовому `value`, это противоречие.
- В `truck-profile.example.json` нет JSON-схемы, а поля осевой нагрузки и класса опасного груза отсутствуют, хотя требования их упоминают.

## 2. Ключевые решения, которые нужно принять (до кода)

1. **Платформа MVP:** PWA (быстро, один код) или сразу нативная/кроссплатформенная (React Native / Flutter). Рекомендация: начать с PWA-прототипа, затем перейти на React Native или Flutter.
2. **Картографическая основа:** OpenStreetMap (лицензия ODbL, есть теги `maxheight`, `maxweight`, `hgv`) и/или официальные данные Израиля. Рекомендация: OSM как базовый граф, официальные данные как слой верификации.
3. **Движок маршрутизации:** GraphHopper или Valhalla (оба поддерживают грузовые профили) либо собственный на PostGIS + pgRouting. Рекомендация: Valhalla или GraphHopper, собственный движок не писать.
4. **Бэкенд:** например TypeScript (Node/NestJS) или Python (FastAPI) + PostgreSQL/PostGIS.
5. **Юридическая модель:** ответственность, дисклеймеры, лицензии данных, израильский закон о защите приватности.

## 3. План по этапам

### Этап 0: Гигиена репозитория (1–2 дня)
- [ ] Исправить `README.md`: название, цель, статус «прототип, не для навигации», структура репо.
- [ ] Добавить `LICENSE`, `.gitignore`, `.editorconfig`, `CONTRIBUTING.md`.
- [ ] Унифицировать имена `README.md`.
- [ ] Настроить GitHub Actions: проверка JSON-схем и линтер Markdown.
- [ ] Завести issues и milestones по этапам ниже.

### Этап 1: Требования и данные (2–4 недели)
- [ ] Инвентаризация источников: Нетивей Исраэль, Минтранс (משרד התחבורה), Data.gov.il, муниципалитеты, OSM. Для каждого записать лицензию, формат, частоту обновления, покрытие.
- [ ] Связаться с ведомствами насчёт официального доступа к данным об ограничениях.
- [ ] Юридическая консультация: ответственность, приватность, лицензии.
- [ ] Доработать схему `restrictions.schema.json`: `geometry` (GeoJSON), `verifiedBy`, `source.license`, `source.url`, направление движения, временные окна; разделить числовые и булевы ограничения через `oneOf`.
- [ ] Создать `vehicle-profile.schema.json` (высота, ширина, длина, масса, осевая нагрузка, ADR-класс, единицы, диапазоны).
- [ ] Тесты валидации схем и набор фиктивных примеров.
- [ ] Обновить PRD до v0.2: user stories, критерии приёмки, приоритеты MoSCoW.

### Этап 2: Данные и бэкенд (4–6 недель)
- [ ] Выбрать стек, зафиксировать решения в `docs/adr/` (Architecture Decision Records).
- [ ] Docker Compose: PostGIS + API.
- [ ] Импорт OSM-выгрузки Израиля (Geofabrik) и извлечение грузовых тегов.
- [ ] Пайплайн загрузки ограничений: валидация по схеме, учёт происхождения (provenance), аудит-лог.
- [ ] Модерация: смена статусов `unverified → verified/disputed/expired`, роли проверяющих, напоминания о `reviewDueAt`.
- [ ] API: CRUD профилей ТС, чтение ограничений по bbox/сегменту.
- [ ] Unit- и интеграционные тесты, покрытие ≥ 80% для логики верификации.

### Этап 3: Маршрутизация, safety-first (6–8 недель)
- [ ] Развернуть Valhalla или GraphHopper с грузовым профилем на графе Израиля.
- [ ] Подмешивать к движку проверенные ограничения TrucksIL.
- [ ] Правило: неизвестное покрытие означает предупреждение, а не разрешение. В ответе маршрута указывать участки без данных.
- [ ] Набор эталонных сценариев: низкие мосты, ограничения массы, запреты для грузовиков. Каждый с ожидаемым результатом.
- [ ] Регрессионные тесты маршрутов в CI.
- [ ] «Safety gates»: формальный чек-лист, без которого маршрутизация не включается для пользователей.

### Этап 4: Клиентское приложение (6–10 недель, параллельно с этапом 3)
- [ ] Прототип UI (Figma): профили ТС, карта, маршрут с предупреждениями, таймер смены.
- [ ] i18n: иврит (RTL), русский, арабский (RTL), английский. RTL проверить с самого начала.
- [ ] Профили ТС с валидацией единиц.
- [ ] Таймер смены: старт, перерыв, продолжение, конец; уведомления за 2 ч, 1 ч и 30 мин; дисклеймер «не является юридическим подтверждением».
- [ ] Офлайн-режим и явные состояния ошибок.
- [ ] Согласие на геолокацию, минимальное хранение данных.

### Этап 5: Отчёты водителей и официальные ленты (4–6 недель)
- [ ] Отчёты пользователей (пробки, ДТП, опасности, камеры) с пометкой «не проверено», со сроком жизни и модерацией.
- [ ] Защита от спама и злоупотреблений (rate limit, репутация).
- [ ] Официальные ленты только из аутентифицированных источников и с отдельной атрибуцией. Отчёты пользователей нельзя повысить до официальных.

### Этап 6: Валидация и пилот (6+ недель)
- [ ] Полевая проверка выборки ограничений.
- [ ] Независимый аудит безопасности (данные, маршрутизация, приватность, пентест).
- [ ] Закрытый пилот с 10–30 водителями, сбор обратной связи.
- [ ] Политика удаления данных, privacy policy, условия использования.
- [ ] Публикация в App Store и Google Play. Отдельно оценить CarPlay и Android Auto.

## 4. Ближайшие шаги (следующие 1–2 недели)

1. Исправить README и добавить базовые файлы репозитория (этап 0).
2. Принять решения из раздела 2, хотя бы по платформе MVP и движку маршрутизации.
3. Доработать JSON-схемы, добавить схему профиля ТС и тесты валидации.
4. Начать инвентаризацию источников данных и переписку с ведомствами: это самый долгий и блокирующий пункт.
5. Заменить `index.html` на страницу-заглушку проекта (описание и статус) или удалить.

## 5. Риски

| Риск | Влияние | Митигирование |
|---|---|---|
| Нет доступа к официальным данным | Критическое | Начать переговоры сразу, OSM как временная база, явно показывать отсутствие покрытия |
| Ошибочный маршрут (мост, масса) | Критическое, вплоть до жизни людей | Safety gates, консервативные правила, полевая проверка, дисклеймеры |
| Лицензии данных (ODbL и др.) | Высокое | Юридическая проверка до импорта |
| Приватность геоданных | Высокое | Минимизация, согласие, политика удаления |
| Сложность RTL и 4 языков | Среднее | i18n с первого дня |
